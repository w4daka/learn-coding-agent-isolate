0003 egress を絞る

0002 の結論は二択だった。全開（送信無対策）か全閉（pi が死ぬ）か。今回は第三の道だ。API だけ通す。手段は許可型 proxy。IP 許可ではなく FQDN 許可にする理由まで観測しろ。

知識: なぜ IP 許可では駄目か

お前の provider（opencode-go）の到達先は opencode.ai だ（models-store.json の baseUrl より。鍵の値は読んでいない）。こいつの答えは DNS で変わる。IP を書いた瞬間に腐る。だから L7（名前）で絞る。容器の出口に tinyproxy を置き、allowlist＝opencode.ai のみ、他は 403。これが egress 絞りの定番形だ。

# 叩き台（ホスト側・未検証。動かなければ trace を貼れ）
# 1. フィルタ付 proxy を立てる
docker run -d --name egress-proxy --network isolated-net \
  -v "$PWD/tinyproxy.conf:/etc/tinyproxy/tinyproxy.conf:ro" \
  -v "$PWD/filter:/etc/tinyproxy/filter:ro" \
  tinyproxy/tinyproxy
# tinyproxy.conf: Filter "/etc/tinyproxy/filter", FilterURLs On, FilterDefaultDeny Yes
# filter: 1行だけ opencode.ai

# 2. pi 容器は proxy 経由でのみ外に出る
docker run --rm --read-only --network isolated-net \
  --cap-drop ALL --security-opt no-new-privileges \
  -e http_proxy=http://egress-proxy:8888 \
  -e https_proxy=http://egress-proxy:8888 \
  your-pi-image \
  sh -c 'curl -s -o /dev/null -w "api:%{http_code}\n" https://opencode.ai/; curl -s -o /dev/null -w "other:%{http_code}\n" https://example.com/'
# 期待: api:到達 / other:403。これが「通す物だけ通る」の実物だ。
判定基準: api 到達＋example.com 403 の対照。IP ではなく名前で絞ったから DNS 変動に強い。なお https_proxy 経由でも TLS の中身は見えない（CONNECT 方式）。proxy に見えるのは接続先の名前だけだ。秘密の送信先が名前で監査できる。これが観測可能性の egress 版だ。
