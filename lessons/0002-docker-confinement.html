0002 Docker で pi を閉じ込める

bwrap 檻は動いた。だが net が全開だ。送信脅威は未対策のまま残っている。今回は Docker で束の境界（FS・net・capability）を扱い、送信を閉じると pi が死ぬことを観測する。それが次回（egress 絞り）への布石だ。

知識: Docker の境界と警告

bwrap との差は3点だ。① FS・net・cgroup・capability・seccomp を束で制限できる。② 使い捨て（--rm）が標準。③ docker デーモンは root だ。 docker グループ所属＝実質 root 取得と同等。お前は既に docker グループ入りしている（id で確認済み）。pi に docker ソケットを見せるな。見せた瞬間、檻の外側が root になる。

旗効果bwrap 対応物
--read-onlyrootfs 全体が EROFS。書込は tmpfs 指定場所のみ--ro-bind / 相当
--cap-drop ALL＋--security-opt no-new-privileges権限昇格の芽を潰すuser ns＋NO_NEW_PRIVS 相当
-v "$HERE:/work:rw" のみ書けるのは workspace だけ--bind HERE HERE
--network none送信ゼロ。ただし pi も死ぬ（後述）（bwrap 檻は未対策）

技能: ホスト側で実行しろ（agent は檻内のため未検証の叩き台だ）

# 実験A: 読取専用 rootfs の観測（pi 不要・5分）
docker run --rm --read-only \
  --cap-drop ALL --security-opt no-new-privileges \
  --tmpfs /tmp:rw,noexec,nosuid,size=50m \
  -v /tmp/pi-isolate-lab/work:/work:rw \
  archlinux:base \
  sh -c 'touch /should-fail; echo "exit=$?"; touch /work/ok && echo "work-writable"'
# 期待: Read-only file system / exit=1 / work-writable

# 実験B: net を切ると pi が死ぬ観測（送信と機能の衝突）
docker run --rm --read-only --network none \
  --cap-drop ALL --security-opt no-new-privileges \
  your-pi-image \
  sh -c 'getent hosts api.anthropic.com; echo "exit=$?"'
# 期待: 解決失敗。pi は LLM API に届かず起動不能。これが送信対策の代償だ。
判定基準: A=EROFS＋work 書込可、B=名前解決失敗。B の死に方が「送信を閉じる代償」の正体だ。API 到達のみ許可する egress 絞りは Lesson 0003 の宿題にする。実験はホスト側の別ターミナルで実行し、trace 全文を貼れ（0001 の流儀で）。
